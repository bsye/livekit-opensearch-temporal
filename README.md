# LiveKit self-hosted (local, macOS)

The Linux production setup generated by LiveKit, run locally on macOS with
[OrbStack](https://orbstack.dev) (its `network_mode: host` behaves like Linux).

## Quick start

```sh
npm run meet                    # or: scripts/meet.sh [room] [identity]
npm run stop                    # native services; `npm run stop -- --all` also stops Docker + unloads the LLM
```

`scripts/meet.sh` starts whatever isn't running yet (docker compose stack, LM Studio + model,
mlx-audio, Temporal worker, webhook translator, voice agent), waits until each is ready, then
opens Meet in a new room (default `meet-<HHMMSS>`) that the agent joins automatically. It
prints the room's Temporal workflow link. Native services run detached with logs in `.run/`.
One-time prerequisites are under [One-time setup](#one-time-setup).

| Service | Address |
|---|---|
| LiveKit signaling (browsers) | `wss://livekit.localhost` |
| LiveKit signaling (backends, CLI, agents) | `ws://localhost:7880` |
| WHIP ingress | `https://whip.localhost/w` |
| RTMP ingress | `rtmp://livekit.localhost:1935/x` |
| Temporal UI | http://localhost:8233 |
| Temporal gRPC | `localhost:7233` (namespace `default`) |
| Webhook translator | `http://localhost:3100/webhook` |
| Speech (STT + TTS, mlx-audio on the GPU) | `http://localhost:8000/v1` |
| LLM (LM Studio) | `http://localhost:1234/v1` |
| Action gate (Laya, MLX) | `http://localhost:8100/v1/systemone` (Jev-compatible) |

Credentials are in `.env` (template: `.env.example`; must match `keys` in `infra/livekit/livekit.yaml`).

## Layout

```
docker-compose.yaml   all services; run docker compose from the repo root
infra/<service>/      config mounted into each container (livekit, ingress, egress, redis, caddy, temporal)
infra/linux/          original Linux production installer, for reference
data/                 runtime data written by containers (gitignored; data/caddy holds the local CA)
apps/livekit-temporal/ LiveKit webhook → Temporal translator + RoomSession workflow worker (TypeScript)
agents/voice-agent/   local voice agent (Agents SDK, TypeScript) reporting to Temporal
services/mlx-audio/   native MLX speech server (Apple GPU), run outside Docker
services/laya/        native MLX Laya decision server for the action gate (Python model sidecar)
package.json          npm workspaces (apps/*, agents/*); run `npm install` at the root
```

## Room sessions in Temporal

LiveKit posts webhooks (`webhook` in `infra/livekit/livekit.yaml`) to the translator in
`apps/livekit-temporal`, which verifies them and signal-with-starts one `roomSession`
workflow per room session:

- workflow id = room sid (`RM_…`); search attributes `RoomName`, `ParticipantIdentities`
- each webhook is a `livekitEvent` signal in the workflow history (duplicates are ignored by event id)
- `room_finished` completes the workflow after a 1-minute grace period for late webhooks;
  late events after that are dropped (reuse policy `REJECT_DUPLICATE`)
- query `roomState` for the live participants/tracks view
- each participant gets a `participantSession` child workflow (id `RM_…/<identity>`), shown
  as its own labelled lane in the room's timeline: 🏠 room, 👤 user, 🤖 agent, 📥 ingress,
  📤 egress, ☎️ SIP. It holds that actor's events, transcript lines and (agents) metrics;
  query `participantState`. Temporal colours events by type, so lanes and labels are how
  actors are told apart.
- signals are *named* after who did what (`👤 dalbi · track_published (AUDIO)`,
  `🤖 agent-…: “The capital of France is Paris”`, `🤖 agent-… · ⏱ voice-to-voice 1500ms`)
  because the timeline labels signals by name; the payload is a typed `RoomSignal` envelope,
  accepted via the workflows' default signal handler (`signalLabel` in `shared.ts`)

```sh
cd apps/livekit-temporal && npm install
npm run worker        # terminal 1
npm run translator    # terminal 2 (port 3100; 3000 is used by another project)
```

Filter in the UI with `RoomName="test"` or `ParticipantIdentities="me"`. From the CLI:

```sh
docker compose run --rm --no-deps --entrypoint temporal -e TEMPORAL_ADDRESS=temporal:7233 \
  temporal-namespace workflow query --workflow-id RM_xxx --name roomState
```

Temporal runs from `temporalio/server` with the vendored env-driven config in
`infra/temporal/config.yaml`; the one-shot `temporal-schema` and `temporal-namespace`
services (`infra/temporal/setup.sh`) create the Postgres schema, namespace and search
attributes on every `docker compose up`.

## Voice agent (local models, Apple GPU)

`agents/voice-agent` runs a fully local pipeline and reports every conversation turn
and pipeline metric to the room's Temporal workflow:

```
Silero VAD → Parakeet STT (mlx-audio) → LLM (LM Studio) → Kokoro TTS (mlx-audio)
                                   └─ signals: transcript, agentMetrics → roomSession workflow
```

Everything runs natively on the GPU: Docker on macOS can't use Metal, so the speech
server (`services/mlx-audio`) and LM Studio run outside compose. Models and endpoints
are set in `.env` (`LLM_*`, `SPEECH_BASE_URL`, `STT_MODEL`, `TTS_*`).

Measured on an M5 Max:

| Stage | Model | Latency |
|---|---|---|
| STT | `parakeet-tdt-0.6b-v2` (whisper-large-v3-turbo: ~720ms, multilingual) | ~60–110ms |
| LLM first token | `gemma-4-26b-a4b`, `reasoning_effort: none` | ~530–620ms |
| TTS first audio | `Kokoro-82M-8bit` (bf16: ~390ms) | ~200ms |
| Voice-to-voice | `turn_latency` metric | ~2–2.7s |

Turn-taking is tuned in `agents/voice-agent/src/agent.ts`: LiveKit's audio turn detector
(`inference.TurnDetector` v1-mini, open weights, local CPU, bundled in `@livekit/agents`)
decides from intonation whether a pause ends the turn, after 300ms VAD silence and within
300–2500ms endpointing; barge-in needs 600ms and 2+ words; the LLM (not TTS) starts
preemptively on the final transcript. v1 (more accurate) only runs on LiveKit Cloud. Tighter settings split sentences at natural pauses
and let "okay" or echo interrupt the agent, which then restarts its reply. Use headphones:
on laptop speakers the mic picks up the agent's own voice.

One-time setup and run:

```sh
npm install                                   # repo root (workspaces)
~/.lmstudio/bin/lms server start
~/.lmstudio/bin/lms load google/gemma-4-26b-a4b -y
services/mlx-audio/run.sh                     # creates its venv on first run, warms up models
npm run dev -w voice-agent                    # plus the worker and translator from above
```

The agent is auto-dispatched to every new room: join one from Meet and talk to it. Each
turn shows up in the room's workflow history as `transcript` and `agentMetrics` signals
next to the `livekitEvent` signals from webhooks (query `roomState` for the collected view).

Notes:
- The LLM must honour `reasoning_effort: none`. `gemma-4-e4b` doesn't: with thinking
  disabled it reasons out loud in the reply, and with it enabled it thinks for 1–7s.
- Scripted test users with `lk room join --publish` must pass `--auto-subscribe`: the
  agent's speech only plays out (and gets recorded as a finished turn) when someone is
  subscribed to its audio.
- Startup warnings about the cloud turn detector and session events are LiveKit Cloud
  features falling back to local equivalents.

## Tools: risk tiers, approval and audit

Tools (`agents/voice-agent/src/tools.ts`) are tiered by risk, like the OpenAI Agents SDK's
`needsApproval` and ChatGPT's "ask before consequential actions":

| Tier | Tools | Behaviour |
|---|---|---|
| Reversible | `set_reminder`, `cancel_reminder` (undo) | runs immediately, reads back what it did |
| Consequential | `send_email` (simulated) | `needsApproval`: confirmed with the user first |

Approval (`approval.ts`) uses LiveKit primitives: the tool pauses inside its own `execute`,
runs a small confirmation `AgentTask` through `ctx.foreground()` (spoken verbatim with
`session.say`, then an `approve`/`reject` tool picked by the LLM), and only continues on
approval. The LLM can't skip it or claim success early, because the tool is still running.

Laya audits every committed action afterwards (`audit.ts`, off the critical path) and the
result is a signal in the agent's lane (`🔎 … audit set_reminder ok 0.74`, `⚠️ … flagged`).
Zero-shot audit scores are noisy (they flag some correct actions); they're for review and for
collecting labelled data to fine-tune Laya, not for blocking.

Side effects are Temporal workflows: `reminder` (durable timer, cancelled by undo) and
`sendEmail` (simulated outbox). `services/laya/eval_gate.py` documents why Laya isn't used as
a blocking gate: it approved "50 euros" → `amount=500` at p=1.00.

## Differences from the Linux setup

- `rtc.use_external_ip: false` in `infra/livekit/livekit.yaml` and `rtc_config.use_external_ip: false`
  in `infra/ingress/ingress.yaml`. With `true`, LiveKit advertises the public IP found via STUN,
  which isn't reachable from a laptop behind a router. Add `node_ip: <LAN IP>` if
  devices other than this Mac need to connect.
- Caddy can't install its local CA from inside the container, so it's trusted
  manually on the Mac (below).

## One-time setup

```sh
brew install livekit-cli

# start once so Caddy creates its CA, then trust it in the macOS keychain
docker compose up -d
sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain \
  "$PWD/data/caddy/pki/authorities/local/root.crt"
```

Firefox: set `security.enterprise_roots.enabled=true` in `about:config`.
Node.js clients on `wss://`: `export NODE_EXTRA_CA_CERTS="$PWD/data/caddy/pki/authorities/local/root.crt"`.

## Run

```sh
docker compose up -d        # start
docker compose ps           # status
docker compose logs -f livekit
docker compose restart livekit ingress   # after editing infra/livekit or infra/ingress config
docker compose down         # stop

curl https://livekit.localhost           # should print OK
```

## CLI

Load the credentials into your shell (`lk` and the Agents SDK read these variables):

```sh
set -a; source .env; set +a
```

```sh
# join token for a browser client
lk token create --join --room test --identity me --valid-for 24h

lk room list
lk room participants list test

# join a bot that publishes demo video
lk room join --identity bot --publish-demo test
```

Test in a browser: https://meet.livekit.io → **Custom** → server `wss://livekit.localhost` + the token.

## Debugging media

- Browser: `chrome://webrtc-internals` — selected candidate pair, `outbound-rtp` /
  `inbound-rtp` stats and bitrate graphs.
- Server: `docker compose logs -f livekit | grep -E 'participant active|mediaTrack published|ice'` —
  `participant active` shows the selected ICE candidates and `connectionType`
  (`udp` is best; `tcp`/`turn` means a fallback).
